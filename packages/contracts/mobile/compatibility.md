# SDK compatibility and release policy

Both SDK implementations target mobile contract v1. Package versions are independent of the wire version. Use the versioned installation instructions in each SDK guide and verify that exact npm version or Swift package tag exists. Source conformance evidence alone does not establish publication or acceptance of a different revision.

This matrix describes required support and test location. Exact run outcomes, compiler/platform evidence and remaining release blockers belong in `PROGRESS.md` and SDK release documentation. A missing runner or skipped fixture never counts as passing. Device, publication and purchase acceptance are separate from source conformance.

For a client-facing change:

1. Review the intended behavior and compatibility impact. Add or update schemas, constants, behavior rules and language-neutral scenarios/vectors together.
2. Implement the capability in every supported SDK. If an intentional gap remains, record the gap explicitly with API/install guidance; do not silently mark the capability supported.
3. Regenerate exports and native constants, then run artifact drift, both SDK suites and server tests using real local PostgreSQL. Keep historical payload vectors.
4. Update SDK guides, agent handoff/setup instructions and this capability matrix. Verify the actual package in a clean consumer, not only a monorepo import.
5. Deploy backward-compatible server support before releasing clients that send new fields. Publish each SDK independently with changelog/compatibility evidence, then update copied installation versions to packages that really exist.

Never weaken validation to make a failing scenario pass without reviewing its intended behavior. Never remove historical payload compatibility just because the latest SDK changed. Breaking behavior requires an explicit migration/deprecation policy and a new contract boundary where appropriate. Server-only report changes usually need neither SDK release; platform fixes still run shared conformance to detect regressions.

## Version compatibility notes

Wire, storage and identity effects of each SDK release. What changed for app developers, and what an upgrade needs, is in the changelogs ([React Native](https://appbase.so/docs/sdk-changelog.md), [Swift](https://appbase.so/docs/swift-sdk-changelog.md)).

React Native 0.12.0 and Swift 0.11.0 send to `https://in.appbase.so` when the app passes no API URL; it serves the same API, and an explicit URL (including `https://api.appbase.so` from earlier setups) is used as before. They keep wire schema v1, the storage namespace (`mobile-analytics:v1:<app>:production` from the `ma_prod_` key) and stored identities and queues; other key formats are refused at creation. Stored state gains an optional `delivery` record (persisted server waits, blocks, a 410 stop and `control`, tied to a key fingerprint), which older SDKs ignore after a downgrade. Requests add `X-Appbase-SDK` and `X-Appbase-Dropped`; the API records them from migration 056 and ignores them before. Responses may carry `control` and the API answers 410 for retired keys; older SDKs ignore `control` and block on 410 as on any other 4xx. New IDs are UUIDv7, which every server version accepts. Unreadable stored events are dropped and counted rather than failing creation; an unreadable identity root still fails closed. The API must serve migration 056 before these SDKs are used for `sdk_versions` to fill; collection works without it.

React Native 0.11.0 and Swift 0.10.0 keep wire schema v1, storage and identities. `revenuecat_identity_linked` may now omit `revenuecat_project_id`, and stored link state may omit its project; the API (migration 053) matches such a link against every RevenueCat project its app is connected to. An API without migration 053 rejects those links, so it must be live before these SDKs are used (it is since 21 October 2026). Links that name a project behave as before.

React Native 0.10.0 and Swift 0.9.0 keep wire schema v1, storage and identities. A changed onboarding definition under an existing version no longer throws; saved attempts are kept or restarted by the [onboarding rules](https://github.com/appbasehq/appbase-react-native/blob/main/packages/contracts/mobile/behavior.md#onboarding), and an optional `warnings` list in batch responses becomes `configuration` diagnostics. Older servers omit `warnings`; the hosted API (migration 046) keeps changed definitions instead of rejecting their events, for every SDK version.

React Native 0.9.0 and Swift 0.8.0 add `setProfile` (an identified account's email and name for the dashboard) as the `profile_updated` event in wire schema v1, and retry an Unknown build detection in the background. An API without migration 036 would store a profile as an ordinary event, email included; the hosted API has it. Storage and identities are unchanged, and upgrading needs no code change.

React Native 0.8.0 and Swift 0.7.0 add the optional RevenueCat integration (`connectRevenueCat`): it links identity, reports access and records purchases through the existing public APIs, so wire schema v1, storage and recorded events are unchanged and no RevenueCat dependency is added.

React Native 0.7.0 and Swift 0.6.0 keep wire schema v1 and storage unchanged. They reject NUL and unpaired-surrogate text at capture, flush when the app leaves the foreground (React Native), count `app_active` only on returns from the background, reset before identifying a different user, send `identity_linked` only when the user changes, and send `X-Appbase-Sent-At` so the server can correct a wrong device clock (older servers ignore the header). Upgrading needs no code change; apps that relied on `identify` refusing an account switch should still call `reset()` on logout.

React Native 0.6.0 and Swift 0.5.0 detect the build environment automatically (an explicit `runtimeEnvironment` still wins) and accept plain HTTP only for loopback/private-network development hosts. Apps now use one collection key for every build, so the dashboard separates Development, TestFlight and App Store by this field. No wire version, storage namespace or identity change is required; older versions keep working and their unlabelled events count as Production. React Native adds a bundled iOS module, so native apps need `pod install` or a rebuilt Expo development/production build.

React Native 0.3.0 and Swift 0.2.0 shipped the former `markNewUser()` helper. React Native 0.4.0 and Swift 0.3.0 remove that source API and local deduplication behavior by explicit migration. Acquisition now uses a saved server-side event definition. Remove helper calls when upgrading; reuse existing tracking. No collection wire version, storage namespace or identity change is required. Old states and queued marker events remain readable; `legacy-marker-upgrade` verifies both runners. The obsolete helper-only scenarios are removed; generic delivery/consent/storage scenarios remain. Published archives and tags stay immutable. Check release manifests for availability, and see [configured acquisition](https://github.com/appbasehq/appbase-react-native/blob/main/packages/contracts/mobile/behavior.md#configured-acquisition).
